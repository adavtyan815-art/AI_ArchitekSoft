# 17 — Quality audit, September 2026

Report date: 17 September 2026. Subject: the whole system as it stands in this repository — public
site, admin panel, client portal, SMM pipeline, worker, deployment files.

This is the record of a full quality pass: what was checked, what was wrong, what was changed, what
was decided without asking you, and what is still open. Nothing here is a plan; every line describes
the code as it is now.

---

## 1. What was done, in order

| # | Pass | What it did |
|---|---|---|
| 1 | Baseline | Built the system as found and walked 51 public and admin URLs at desktop and phone width, so every later measurement had something to compare against |
| 2 | Code audit | Line-by-line reading of the source, then an **adversarial re-check** of every reported issue: each one had to be reproduced against the running system, or it was thrown out |
| 3 | Browser audit | A real Chrome driven through all nine modules at 1440×900 and 390×844, in both admin languages. Every reported defect was then re-checked by a second, independent pass that did not see the first one's reasoning |
| 4 | Design review | The admin panel and the client portal / public forms read against the design system (docs/14_DESIGN_SYSTEM.md) |
| 5 | Fix packages | The confirmed work split into twelve packages by file ownership, so two packages never edit the same file. Each package fixed its own items, then a separate pass re-verified them module by module in the browser, then the cross-package leftovers were integrated |
| 6 | Production regression | The finished system rebuilt and re-tested against a **production** server (`next start`), not the dev server: public site, admin, portal, SMM pipeline, plus a static completeness review of the whole change set. The last findings from that pass were fixed and re-verified |

Two ground rules held throughout: the demo database was never reset or re-seeded, and anything
created for a test was named `QA-…` and deleted afterwards. The closing sweep of every table found no
`QA-` row left; the counts stood at 9 projects, 8 clients, 4 companies, 11 leads, 25 assets, 6
portfolio items, 6 posts, 3 client pages and 5 tasks — the seeded set. No seeded record was deleted,
renamed or edited, the Telegram admin chat id ends empty as it began, and the admin password was
never changed.

## 3. Per module: the important defects and what was done

Severity is the audit's own. "Fixed" means re-checked in a browser after the change.

### Public site and intake forms

| Defect | What was done |
|---|---|
| **high** — An unknown address fell through to the framework's generic English 404 page: no header, no footer, off-brand, untranslated | The site has its own 404 now, in all three languages, with the site chrome and seven links back. It answers HTTP 404. An unknown portfolio slug renders the same page |
| **medium** — No Content-Security-Policy header on any response | Every response now carries one, built per request with a nonce. Checked against a production build: 174 script tags on the home page all carry the nonce, 0 policy violations across 174 page loads |
| **high** — Uploads over 10 MB failed: the framework cut every request body at 10 MB before the route saw it | `/api` and `/media` are out of the middleware's path list, so bodies are no longer copied and truncated. An 11 MB upload was verified to arrive |

## 5. What you will notice

These are deliberate changes in how the system behaves day to day.

**Saving.** Almost every save in the admin now ends with a short confirmation message and a
re-rendered form. This is what killed the "my change did not stick" class of bugs, and it means the
page reloads after a save instead of staying still.

**Stricter validation, including on old data.** A client, company or lead whose stored phone or
e-mail is malformed cannot be saved until that field is corrected. An admin-created lead needs at
least one of phone, e-mail or Telegram — the same rule the public form always had.

**Client page passcodes.** Visitors who had already entered a passcode will be asked once more: the
cookie is now tied to the link. New passcodes must be 6–24 characters; existing shorter ones keep
working.

**Money.** Amounts print as `1,234,567 AMD` in the admin, and totals that mix currencies are printed
one figure per currency instead of being added together.

**Portfolio.** The public portfolio shows only files marked public, and "Create from project"
produces a hidden draft you have to publish yourself. If you pick a private render for a portfolio
item, it will not appear on the website until you mark that file public.

**Social media.** Two new transient statuses (`sending_approval`, `publishing`) appear while a send
or publish is running; anything stuck in them for 15 minutes is released automatically and reported
to the admin chat. Publishing always asks for confirmation. Approving in Telegram no longer publishes
on the spot — it respects the schedule.

**Client pages.** Invalid addresses answer 404 and dead links answer 410, both with the branded page.
File access follows the link's own "allow downloads" setting.

**Leads from the contact form** now store a Telegram handle in its own field rather than in the phone
field.

**Deployment.** `docker compose` must be run with `--env-file .env`, the image build produces the
standalone output it needs, and `package-lock.json` is now part of the repository so a fresh clone
builds. The inbox drop folder has a host path in the compose file. Details in docs/08_DEPLOYMENT.md.

## 6. What is still open

| Item | Why it was left |
|---|---|
| Occasional React "hydration" warnings on admin pages **in development** | The real cause was found and fixed (a component in the shell that loaded the dictionary a second time). What remains is noise from the development server's own streaming, and its own error text names development-only nodes. It does not occur against a production build: verified over 108 production and 72 development page loads |
| Lists cap at 500 rows with "showing 500 of N" | Real paging is a feature. At today's data volume nothing is hidden |
| A few phone tap targets under 40 px outside the footer | The header logo link (34 px), two in-content arrow links on the home page (22–23 px), and the 3D viewer's own control buttons (36 px, part of the third-party component). Changing the header logo geometry at release close was judged not worth it |
| On a 404 page, the language switcher pre-fetches the same address in the other two languages, which are also 404 | Harmless — it shows as two "failed to load" lines in the browser console on that page only |
| No automated test suite | The system is verified by the browser method in docs/10_TESTING_GUIDE.md. A unit and end-to-end suite is the obvious next investment; it would have caught most of the "save reverts the form" family in seconds |

## 7. Repeating this

docs/10_TESTING_GUIDE.md is the manual: the walkthrough per module, the headless browser method with
the two pitfalls that cost the most time here (scope form selectors to the page form, poll for
notices instead of reading the address bar), the data rules, and the commands.

Before any release, the short version is:

```bash
npm run lint
npm run typecheck
npm run build
npm start          # then walk the modules at 1440 and 390 px, in both admin languages
npm run perf       # compare with docs/13_PERFORMANCE.md
```

Lint, type check and build were all clean at the close of this audit.
